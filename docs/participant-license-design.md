# Participant License Design

Status: **implemented**. The trust table is in [Choreography policies](choreography-policies.md#role-licenses); the measured gas is in the commit that introduced it. This page records the design decisions and their reasons.

## What a participant asset is

A `ParticipantMutableAsset` is a **role license**: a certified, sellable seat in a choreography.

- The **certifier** (administrator of the participant Creator policy) defines *what* the license is.
- The **Participant Master** defines *who* may hold it (authorized issuers, organization qualifications).
- The **holder** is the organization that plays the role today. It changes when the license is sold.
- A choreography links a role to the license **address** once. The address is the stable identity; the holder is not.

## Policies are translated from XACML

In the intended architecture, every smart policy is generated by translating an XACML policy; the policies in this repository are hand-written and simulate such translations. Rules and their configuration (issuers per type, qualifications, allowed messages, switches) are therefore **hardcoded in the policy source** as literals, edited by hand, and never set through runtime setters or constructor data. Hardcoded literals are also the cheapest form: no storage at deploy and no `SLOAD` at evaluation. There is one policy per role, with no separate test policies: its rules are tuned to the current test and evaluation scenarios and edited by hand when the scenarios change. Changing a rule means translating and deploying a new policy, then pointing the token or asset to it under the control of the current policy.

## Fields

| Field | Written by | When | Storage | Survives a sale |
| --- | --- | --- | --- | --- |
| Role type (`participantType`) | issuer, passed to `mintWithParticipantType`; the issuer must be listed for that type in the Master | once, at mint | `immutable` (no storage slot) | yes, never changes |
| Organization name (`name`) | holder | any time | `bytes32`, readable on-chain | no, reset on sale |
| Organization profile (`profile`, was `descriptor`) | holder | any time | `bytes32` hash or CID of an off-chain document (contacts, endpoints) | no, reset on sale |
| Messages | holder, as a subset of the messages the certifier allows for the role type | any time | `bytes32[]` + address of the holder who wrote them | yes, marked with their writer |
| `tokenURI` | nobody: computed by a renderer | on read | none | n/a |

Removed: capabilities (`setCapabilities`, `getCapabilities`, `hasCapability`), the process (`bpmn`, `setBpmn`), `setTokenURI`, `isHolderQualified`, and `setAuthorizedIssuer`.

Decisions behind the table:

- **One license, one type, one qualification.** Capabilities are dropped: a specialization is a type of its own (`SpecialCarrier` instead of `Carrier` + `SpecialTransport`). A role requirement names only a type, and a sale checks a single qualification.
- **The Master defines types and issuers at design time.** Which role types exist, who may mint each of them (`isIssuerOf`), and which organizations may hold each (`isQualifiedFor`) are hardcoded in the Participant Master. There is no setter, so no runtime action can widen who mints or holds what; `mintWithParticipantType` is allowed only to an issuer of the requested type, and the typeless `mint` is denied (and reverts in `ParticipantNMT` anyway). Changing the configuration means deploying a new Master and installing it with `setMasterSmartPolicy`.
- **The type is fixed at birth.** A choreography checks a license only when it links a role to it. A type that could change later would bypass that check, so the type is an `immutable` set in the constructor. It also saves the storage write at mint and makes reading it almost free.
- **Allowed messages per type.** The certifier's Creator policy hardcodes the messages each type may declare (`isAllowedMessage`); its domain check `evaluateMessagesUpdate` allows `setMessages` only when every message is allowed for the license type. Nothing is written per license, and the rule lives in the policy, not in the asset. The Holder policy implements the same check and may only restrict further.
- **Writer tracking instead of reset.** Messages are the role's know-how: a buyer may want to keep them. They carry the address of the holder who wrote them, so a reader can tell whether the current holder stands behind them. The organization profile is the seller's identity and is cleared on sale.
- **No process for now.** The participant's own process (`bpmn`) is removed; if it comes back, it is stored as described in [Process storage](#process-storage-if-re-added), with its own writer address.
- **Computed `tokenURI`.** A stored `tokenURI` is a claim by the holder, who could advertise a type the license lacks. A renderer builds it from on-chain state instead, so a buyer sees only what is true: role type, current holder, profile reference, messages, and whether the messages were written by the current holder. `setTokenURI` and its storage slot disappear.
- **No `isHolderQualified`.** No contract calls it. Qualifications are checked when the license is sold; a later revocation blocks future sales to that organization and is visible in the on-chain history and through `isQualifiedFor`. With hardcoded qualifications, a revocation is a new Master policy.
- **Role relinking is unchanged.** Selling the license changes the organization; relinking a role in the choreography (`setRoles`) changes the license, and the choreography Creator decides which roles are protected from it.
- **Replaceable Master, as in the original NMT project.** `masterSmartPolicy` and `evaluatedByMaster` move into the base `NMT` (removing the copy in each concrete NMT) as a storage variable, with `setMasterSmartPolicy(address)` evaluated by the current Master. Both Master policies recognize that action explicitly. All three policies are then replaceable, each under the control of the current one: Master per NMT, Creator and Holder per asset. This restores `principalSmartPolicy`/`setPrincipalSmartPolicy` of the original `NMT-contracts` project, fixing its action signature (it encoded `setPrincipal(address)`, which no policy recognized). Measured cost: +211 bytes of `ChoreographyNMT` runtime (22,125 → 22,336) and about +2,100 gas on every mint, version, and transfer, for the cold `SLOAD` of the policy address.
- **Renderer fixed in the NMT.** The renderer address is an `immutable` of `ParticipantNMT`, set in its constructor, as in `ChoreographyNMT`. It costs no gas to any transaction; a new JSON format means deploying a new NMT.
- **BPMN labels are unchanged.** The generated BPMN names a participant by its choreography role name; the license address is the technical identity, the type and holder appear in the license `tokenURI`.

## Measured gas

Same accounts and inputs, before and after the license redesign (Hardhat, optimizer 200). The license flow is: issue a `SpecialCarrier` license, set name and profile, declare five messages, sell it.

| Operation | Before | After | Δ |
| --- | ---: | ---: | ---: |
| Deploy participant Master | 776,680 | 486,262 | −37.4% |
| Deploy `ParticipantNMT` (+ renderer after) | 3,238,622 | 3,817,671 | +17.9% |
| Deploy participant Creator | 351,974 | 502,425 | +42.7% |
| Deploy participant Holder | 299,621 | 323,604 | +8.0% |
| Configure the buyer's qualifications (2 tx before) | 89,204 | 0 | −100% |
| Issue a license (mint + type + capabilities before, one mint after) | 1,857,637 | 1,249,297 | −32.7% |
| Holder sets name | 75,351 | 66,674 | −11.5% |
| Holder sets profile (`setDescriptor` before) | 75,774 | 67,102 | −11.4% |
| Holder declares 5 messages | 191,966 | 209,076 | +8.9% |
| Sale to a qualified buyer | 119,461 | 106,910 | −10.5% |
| **Whole flow** | **7,076,290** | **6,829,021** | **−3.5%** |
| **Per license** (issue, data, messages, sale) | **2,320,189** | **1,699,059** | **−26.8%** |

Deploys grow because the renderer and the hardcoded rules are code, paid once; every license is cheaper because the asset is smaller (runtime 7,492 → 5,103 bytes), the type is an `immutable`, and qualifications cost nothing at runtime. `setMessages` costs more because it now runs the Creator AND Holder domain check and records the writer.

## Process storage (if re-added)

The process is not stored today. This section records how to store it if it comes back.

The process is the BPMN of what the participant does on its side (its private process). Only humans and off-chain tools read it: no contract ever looks inside it. What the chain must guarantee is not *storing* it but *proving which one it is*.

### Recommended: hash + URI

The holder stores two small values:

```text
processHash = sha256(process.bpmn)          // bytes32, 1 storage slot
processURI  = "ipfs://bafk…" or "https://…"  // where the file can be downloaded
```

Reading it:

1. Read `processHash` and `processURI` from the license (or from its `tokenURI`).
2. Download the file from `processURI`.
3. Compute `sha256` of the downloaded bytes and compare it with `processHash`.

If they match, the file is exactly the one the holder declared on-chain; if the server lies or the file was edited, the hashes differ. The URI only says *where* to look; the hash says *what* must be found there.

With IPFS the two can collapse into one value: a CIDv1 with the `raw` codec is built from the sha256 of the bytes, so the CID itself is both locator and hash. Keeping a separate `bytes32` hash works with any URI (IPFS, HTTPS, a repository), so it is the default.

### Why not the whole XML on-chain

Storage costs about 22,100 gas per new 32-byte slot, plus 16 gas per non-zero calldata byte. For a process of size *N* bytes:

| Storage | Slots written | Approximate gas, first write |
| --- | --- | --- |
| Whole XML, 2 KB | ~65 | ~1.4 M |
| Whole XML, 10 KB | ~321 | ~7.2 M |
| Hash + short URI (~60 bytes) | ~4 | ~90 k, whatever the size of the process |

The cost of the full XML grows with the process and quickly approaches the block gas limit; hash + URI costs the same for a 1 KB or a 1 MB process. The trade-off is availability: the file must stay reachable at its URI (pinning it on IPFS, or keeping it in the repository). Integrity is never lost: a missing or altered file is detected by the hash check.

These figures are estimates; the implementation will report measured gas as required by [contract structure](contract-structure.md).

## Follow-ups (separate changes)

- **Choreography policies:** the no-setter rule is general; the setters of the choreography policies became deviation 14, since fixed: the choreography Master and Creator are hardcoded, with variants as separate policies (`CreatorSmartPolicyTestScenario`, `CreatorSmartPolicyPaperScenario`).
